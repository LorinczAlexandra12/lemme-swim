# `data/` — Data Sources and Maintenance

This directory contains the application's complete dataset. It includes two
distinct kinds of data:

| File | Contents | Maintained by |
| --- | --- | --- |
| `pools.json` | Pools, basins, and opening hours | `npm run build:dataset`, generated from files in `research/` |
| `blocks.json` | **Lane bookings** (which lanes are occupied and when) | `npm run scrape` and manual maintenance |
| `schedule-sources.json` | Per pool: where lane data comes from and when it was collected | `npm run scrape` for scraper data; manual maintenance for `curated` data |
| `research/*.json` | Raw research notes for each pool | Manual maintenance |
| `.cache/` | Raw responses downloaded by scrapers | `npm run scrape`; safe to delete at any time |

> `pools.json` and `research/` are outside the scope of this document. This guide
> describes the provenance of lane schedules.

---

## 1. How Machine-Readable Are Budapest Pool Schedules?

In short: **very few are.** We reviewed every pool documented in `research/`.
Here is what we found:

* **One** pool publishes a genuine HTML **table**: BVSC-Zugló's embedded
  FacilityPilot booking calendar.
* Four more pools publish **machine-readable but non-tabular** schedules: two
  PDFs encode occupancy using cell **fill colors** (Csepel and Újhegyi); one PDF
  uses the same color coding with a decodable legend (TVE); and one provides a
  plain-text HTML list (Tüskecsarnok).
* Two pools publish their *best-quality* schedules as **images** (a PNG for
  Kispest and a JPG for Dagály), so these are entered manually.
* For the others (Császár-Komjádi, Duna Aréna, Hajós Alfréd, Ferencváros, Újlak,
  Újpest, Nyéki Imre, and others), **no lane schedule is published** in any
  format, or it appears only in Facebook images.
* There are **no** iCal/ICS calendars, public APIs, or JSON endpoints providing
  lane schedules. (The WordPress `wp-json` media library lists uploaded image
  and PDF files, but does not expose the schedules themselves.)

Each source therefore has its own **hand-written adapter**; there is no common
schema, standard, or API for these schedules.

## 2. `blocks.json` Structure

```jsonc
{
  "note": "…",
  "curatedPools": ["kispesti-uszoda", "dagaly-furdo-es-uszoda"],
  "blocks": [
    {
      "poolId": "kispesti-uszoda",        // Must match the pool ID in pools.json
      "basinId": "33m-uszomedence",       // Basin ID within this pool
      "weekday": 1,                       // Exactly one of date or weekday; 1 = Monday ... 7 = Sunday
      "start": "08:00",                   // 24-hour time, HH:MM
      "end": "09:00",                     // Must be later than start
      "lanesOccupied": 1,                 // Number of occupied lanes, not a lane number
      "kind": "club",                     // club | school | course | event | maintenance | closed
      "reason": "…"                       // Hungarian explanation displayed to users
    }
  ]
}
```

Two rules are easy to get wrong:

1. **`lanesOccupied` is a count, not a lane number.** If lanes 5, 6, and 7 are
  occupied, set `lanesOccupied: 3`.
2. **Overlapping blocks for the same basin are added together.** Never enter
  overlapping blocks for the same basin and date; otherwise the available lane
  count will be understated. Every adapter has a test for this behavior.

## 3. Running the Scrapers

```bash
npm run scrape                       # all adapters, using the cache
npm run scrape -- --dry-run          # preview results without writing files
npm run scrape -- --only=bvsc-facilitypilot
npm run scrape -- --no-cache         # bypass data/.cache and fetch fresh data
```

The command prints its summary in Hungarian and exits with a **non-zero status**
if any adapter fails. This is intentional: a scraper that silently returns an
empty result is worse than one that reports an error.

**Politeness measures** (in `src/lib/scrapers/http.ts`): a descriptive
User-Agent, a 20-second timeout, at least a one-second delay between requests to
the same host, `robots.txt` compliance, and a six-hour disk cache in
`data/.cache/`. The cache can be deleted at any time; the next run will recreate
it.

### Data Provenance: `schedule-sources.json`

`pools.json` is generated by `npm run build:dataset`, so direct edits will be
lost on the next build. Data provenance is stored separately:

```jsonc
{
  "_comment": "…",
  "sources": {
    "csepeli-strandfurdo": {
            "type": "scraper",            // scraper | curated | none
      "adapter": "csepel-palyabeosztas",
      "url": "https://www.csepelistrandfurdo.hu/palyabeosztas/",
      "lastScrapedAt": "2026-09-24T16:45:27.401Z"
    }
  }
}
```

`build-dataset.ts` overlays this on the default `{"type":"none"}` source in
`pools.json`. **If a pool is missing from this file, the UI says “No lane data,”
even if blocks exist for it.**

Each `npm run scrape` run updates this file using a read-modify-write process:

* Only pools handled by **successful** adapters receive a new `lastScrapedAt`.
  Failed adapters are left untouched, so their timestamps age accurately in the
  UI instead of being presented as fresh.
* Entries with type `curated` and the `_comment` key are **not overwritten**.
* Manually added fields such as `format` and `note` are preserved.

To add a source, create a module under `src/lib/scrapers/adapters/` that calls
`registerAdapter`, then add an import in `src/lib/scrapers/index.ts`. An adapter
must **never return an empty result as a success**: throw an error if the source
cannot be parsed.

## 4. Adding and Updating Curated Schedules

Some pools publish their best-quality schedules as **images** (Kispest PNG,
Dagály JPG). These schedules are interpreted visually and entered manually in
`blocks.json`.

### The `curatedPools` Safeguard

`npm run scrape` **never overwrites** blocks for pools listed in the
`curatedPools` array in `blocks.json`, even if an adapter is added for one later
(the run reports “Keeping curated data”). If a pool switches to scraper data,
**remove its ID from this array**; otherwise the scraper results will never be
used.

### Procedure

1. Open the source (image, PDF, or opening-hours table) and **record its URL and
  the date you checked it**.
2. Determine **how many lanes are occupied** in the basin during each interval.
  If the source lists *free* lanes, subtract that number from the basin's total
  lane count (`pools.json` → `basins[].lanes`).
3. Add the blocks to the `blocks` array in `blocks.json`, and add the pool ID to
  `curatedPools`.
4. Validate the data with
  `npx tsx -e "import {loadBlocks} from './src/lib/data'; console.log(loadBlocks().length)"`.
  This also runs the validation performed when the data is loaded.
5. Add the pool under the `sources` key in `schedule-sources.json`. Otherwise,
  the UI will not show the data, even if the blocks are present in
  `blocks.json`:

   ```json
  { "type": "curated", "url": "<source URL>", "format": "image", "lastVerified": "2026-09-24" }
   ```

### The `lastVerified` Rule

**Every manually maintained pool must have a `lastVerified` date in its
`scheduleSource` entry in `pools.json`.** Curated data has no `lastScrapedAt`, so
this is the only indication of when it was last confirmed. Whenever you review a
curated schedule, **update `lastVerified` to the date you actually checked the
original source**, even if no data needed to change.

### Manual Data Entry Guidelines

* **Never invent a schedule.** Record only what the source states. If a source
  provides public opening intervals but no lane-by-lane schedule, model only
  those intervals and note in `reason` that the data is not lane-specific.
* **Dated blocks expire.** Kispest and Dagály publish weekly schedules, so their
  blocks apply to a specific week. Replace or remove old blocks when a new week
  is published.
* **Do not guess when a legend combines categories.** For example, the Kispest
  schedule does not distinguish “Occupied” from “Closed.” Use the more general
  `kind` and explain in `reason` that the source does not distinguish them.
